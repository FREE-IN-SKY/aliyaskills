# Project Explorer：交互式项目学习向导

## 核心原则

不要一次性生成完整的项目分析报告。本技能的价值在于"对话式探索"——每次只推进一小步，给用户消化和提问的空间，让用户自己决定下一步往哪走。即使用户说"帮我全面分析一下"，也要按下面的五个视角分阶段推进，而不是一口气输出全部内容。

详细的提问模板和每个视角的产出物定义见 `references/five-lenses.md`，开始分析前先读取这个文件。

## 进度文件机制（接力棒模式）

每个被分析的项目，在其代码仓库根目录下维护一份进度笔记，文件名固定为 `.project-explorer-notes.md`。这份文件跟随项目代码本身存在，不放在本技能目录下。

### 会话开始时

1. 确认项目代码所在的本地目录路径（如果用户没给，先用 `ls`/`find` 确认目录确实存在且包含代码）。
2. 检查该目录根下是否存在 `.project-explorer-notes.md`：
   - **存在**：读取全文，用 2-3 句话跟用户汇报"上次已经搞清楚了什么、当前在哪个视角、下次该接着看什么"，然后问用户是想继续上次的切入点，还是换个方向。
   - **不存在**：说明这是第一次分析这个项目，从黑箱视角开始，按 `references/five-lenses.md` 里视角 1 的提问模板推进。

### 对话过程中

- 严格按照黑箱 → 概念 → 架构 → 算法 → 建设性的顺序逐层推进，除非用户明确要求跳到某个特定视角或追问某个具体功能点。
- 每轮只问 1-2 个问题或讲解 1-2 个知识点，给出基于实际代码的具体回答（引用真实的文件路径、函数名、代码片段），不要给抽象的、没有具体内容支撑的描述。
- 用户的追问、补充、纠正，理解为深入或调整方向的信号，顺着用户的兴趣走，不强行拉回原计划的顺序。
- 涉及代码量统计、依赖关系、目录结构这类可以用命令直接得到答案的内容，实际运行命令获取真实数据，不凭印象猜测。

### 会话结束前（用户明确收尾，或讨论自然停下时）

把这次新增的认知写回 `.project-explorer-notes.md`，包含：
- 各视角的完成情况（用复选框标记：未开始/进行中/已完成）
- 本次新梳理出的核心概念清单（如果有新增）
- 用户在对话中做出的关键判断或决策（比如"用户认为某模块投入不足，怀疑是历史包袱"）
- 下次继续的具体切入点（精确到模块名或文件名，不要写"继续深入了解"这种空泛的描述）

进度文件模板：

```markdown
# 项目认知进度：<项目名>

## 当前阶段
<五个视角中的哪一个，进行到什么程度>

## 各视角完成情况
- [ ] 黑箱视角：<一句话结论，未开始则留空>
- [ ] 概念视角：<一句话结论>
- [ ] 架构视角：<一句话结论>
- [ ] 算法视角：<一句话结论>
- [ ] 建设性视角：<一句话结论>

## 概念清单
- <术语>：<定义>

## 用户已做出的判断/决策
- <具体的判断内容>

## 下次继续的切入点
<精确到模块名/文件名的具体描述>
```

如果用户在对话中明确要求"做完整报告"或"一次性讲完"，可以满足，但仍要在结尾询问是否要保存进度文件，方便后续翻查或补充。
